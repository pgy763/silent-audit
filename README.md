# silent-audit

**判断一个脚本的「我干完了」到底可不可信。**

它跑完了，退出码 0，还打印了一句 `迁移完成，处理 1000 行`。
**但文件一个字节都没变。**

这种失败不报错、不抛异常、不留日志。你只有事后去 `git diff` 才会发现。
`silent-audit` 把这件事变成一条命令。

![跑脚本 → 它说完成了 → 数一下，0 行 → silent-audit 判决](docs/demo.gif)

同样的输出，文字版：

```
$ silent-audit run migrate.py

  不可信：它说的话和事实对不上

  可信度  ██░░░░░░░░░░░░░░░░░░  1.0/10

  它声称     处理 0 项
  系统调用    1 次写入 / 2 次读取
  物证      1 个文件被写 · 其中 0 个真的变了
  退出码     0

  ✗ 退出码 0，报告成功，但磁盘上没有任何文件发生变化
    它跑完了、没报错、打印了成功信息，但所有文件的 md5 与运行前一致。

  ! 1 个文件被写过，但内容与运行前逐字节相同
      · conf.json

  最可疑的几行
      10  r.get("url", "")
          代码里写 "url"，数据里的字段是 "URL"，取值会永远失败
```

第二种形态：**写是写了，写错了地方**。

```
$ silent-audit run overwrite.py

  可疑：有实打实的写入，但报告偏乐观

  可信度  ███████░░░░░░░░░░░░░  3.5/10

  ✗ 1 个新建文件看起来是某个已有文件的副本，而不是覆盖它
    文件名带 (1) / copy / -1 这类后缀，同目录下还留着原名那份。脚本会报告
    "已保存"，你的下游脚本却还在读那个没被更新的旧文件。
      · data(1).csv  ← 本应写入 data.csv
```

## 它凭什么下这个结论

三路独立证据，对不上就报警：

| 证据 | 来源 | 回答的问题 |
|---|---|---|
| **它声称** | 脚本的 stdout / stderr | 它说自己做了什么 |
| **它调用** | `sys.addaudithook` 记的真实 `open` / `rename` / `remove` | 它实际动了什么 |
| **物证** | 运行前后的文件 md5 | 世界到底变了没有 |

关键设计：**不需要改被测脚本一个字符**。审计钩子是 Python 解释器提供的，
在进程内部记录，目标代码完全不知道自己在被观察。

## 装

```bash
pip install -e .
# 或者不装，直接跑
python -m silentaudit run script.py
```

Python ≥ 3.9，零依赖。

## 用

```bash
# 最基本
silent-audit run migrate.py

# 盯住指定目录（默认盯脚本所在目录）
silent-audit run clean.py --watch ./cache --watch ./build

# 被测脚本自己的参数，放在 -- 后面
silent-audit run migrate.py --watch ./data -- --dry-run --verbose

# 写一份 JSON（给 CI / 别的程序用）
silent-audit run migrate.py --json report.json

# 可信度低于 6 就以非 0 退出，可以塞进 CI
silent-audit run migrate.py --fail-under 6

# 允许脚本正常新建文件（避免把"生成报告"当成"写错地方"）
silent-audit run build_report.py --watch . --allow-new '*.html' --allow-new 'out/*'

# 声明这次只读不写（检查/校验类脚本），不再因为"磁盘没变"扣分
silent-audit run check_links.py --watch . --readonly

# 先看看它抓什么（会在当前目录生成七个失败样本）
silent-audit demo

# 同一个起点连跑两遍，看两次结果一不一致
silent-audit replay migrate.py --watch ./data
```

## 连跑两遍：它稳不稳

`run` 回答的是"这一次跑得对不对"。`replay` 回答另一个问题：**同一件事干两遍，
结果一样吗。**

```
$ silent-audit replay export.py --watch ./data

  不可复现：同样的起点，两次结果不一样

  可信度  ████████████░░░░░░░░  6.0/10
  两次里更差的一次，再扣掉不一致的分

  副本      3 个文件（不碰你的原文件）

  第 1 次  声称 5 · 变了 1 个 · 退出码 0 · 10.0/10
  第 2 次  声称 2 · 变了 1 个 · 退出码 0 · 10.0/10

  ✗ 同样的输入，它两次报的数字不一样（5 → 2）
    这是最直接的证据：这个数字不是从数据里算出来的。可能来自随机数、时间窗口、上一
    次运行的残留，或者是一段没有真实计数的固定文案。
```

关键在于 **`--watch` 里的东西每次都会被重置**。如果直接在原目录跑两遍，第二遍的
输入已经被第一遍改过了，"两次结果不同"是必然的，什么也证明不了。所以先把盯住的
目录镜像一份，每次运行前从镜像重置 —— 两次的起点严格相同。顺带的好处是**整个
过程不碰你的原文件**，脚本写坏了最多写坏副本。

它只比四样东西，都刻意挑有把握的：

| 比什么 | 不一致说明 |
|---|---|
| 退出码 | 输入相同而成功/失败不同，结果不受输入控制 |
| 它自报的数字 | 这个数不是从数据里算出来的（随机数、时间窗、固定文案） |
| 落盘的改动量 | 有非确定性混在里面 |
| 子进程失败次数 | 通常是网络或并发冲突，不是脚本逻辑 |

数字和落盘都一样、只有输出文字不同时，只轻扣 1.5 分 —— 多半是时间戳或批次号，
它不影响结论，但你拿这份输出做 diff 会一直是脏的。比较前会先抹掉路径和 `0.42s`
这样的耗时，否则那条噪音会盖住真正的差异。

`--keep` 可以留下副本目录自己进去看，`--json` 出结构化结果，`--fail-under` 给 CI 用。


## 输出里的「可信度」是什么

不是"代码质量分"，是 **"这个脚本的自我报告有多可信"**。

- `10` —— 它说的、它做的、磁盘上发生的，三边一致
- `6–9` —— 改动是真的，但报告里有些含糊的地方
- `3–6` —— 有实打实的写入，但声称的数字明显对不上
- `0–3` —— 它说的话和事实对不上

一个逻辑完全错误的脚本也可能拿 10 分：**分数高只说明"报告可信"，
不说明业务逻辑正确**。这句话工具里也会打印出来。

## 十三种它认得出来的模式

| 模式 | 表现 |
|---|---|
| 声称成功但零变更 | 退出码 0 + 成功字样 + 所有 md5 不变 |
| 自报 0 项却当成功 | `处理 0 行` 后面接着 `完成` |
| 数字对不上 | 说处理 1000 项，只动了 3 个文件 |
| 无效写入 | 文件被写过，但内容和原来逐字节相同 |
| 只读不写 | 读了 500 个文件，一次都没写 |
| 写到别处 | 真实写入发生在 `--watch` 指定的目录之外 |
| **写错地方** | 本该覆盖 `data.csv`，结果另存成 `data(1).csv` |
| **子进程悄悄失败** | 调 `ffmpeg` 转码失败，忘了 `check=True`，仍然打印「完成」 |
| **写空壳** | `open(...,"w")` 后写入那行被跳过，40KB 的报告变成 0 字节，仍然打印「已生成」 |
| **静默跳过输入** | 7 个文件处理了 6 个，坏的那个 `continue` 掉，仍然打印「处理完成」 |
| 吞掉部分失败 | 输出里有失败/跳过，但退出码是 0 |
| **只读脚本被误判** | `检查完成，共 2 行，0 个问题` 被当成"没干活"—— 加 `--readonly` |
| 源码线索 | 指向 `.get("url", "")` 这种"永远取到空值"的行 |

最后一条只在**已经判定不可信**时才出现 —— 正常脚本不会看到一屏噪音。

「写错地方」这条有个刻意的取舍：只有**名字像副本**（`x(1).csv` / `x copy.csv` /
`x-1.csv`，且同目录下本尊还在）才扣分。单纯"新建了一个没人提过的文件"只作为
提示、不扣分，因为生成报告的脚本天生会新建文件。要压掉误报就加 `--allow-new`。

「写空壳」是这一版补的，因为它比"完全没写"更危险：`open(path, "w")` 在打开的
那一刻就把文件清空了。后面写数据的那行如果被跳过、或者异常被 `except` 吞掉，
你得到的不是一个旧文件，而是一个**存在、能被打开、但内容为空**的新文件。下游
读到它不会报错，只会拿到空数据。

`--readonly` 是给"天生不写盘"的脚本准备的。你写一个链接检查器、一个 schema
校验器，它读了一堆文件、打印「检查完成，共 2 行，0 个问题」——这在默认判据里
和"循环压根没进"长得一模一样，于是一个正常脚本拿 3 分。

**为什么不自动判断？** 因为"读了不写"本身就是最常见的静默失败形态（字段名
大小写拼错、过滤条件恒为 False）。自动放过等于把最长的那根刺拔掉。让用户显式
声明，判错的代价只是一行参数；默认改掉，漏判的代价是好几个 bug。

`--readonly` 只关掉两条判据（"声称成功但零变更"、"读了却一行没写"），其余照常：
子进程有没有悄悄失败、跳过了哪些输入、写没写到目录外，一样会报。

判据分两档：**剩下 ≤16 字节且原本 ≥1KB** → 判空壳，扣 6 分；**体积掉到 1/100
以下但还有内容**（原本 ≥64KB）→ 只提醒，扣 2 分。分两档是因为 4KB 的 JSON 压成
200 字节完全正常，而 40KB 的 HTML 变成 0 字节不正常。第一版用"缩到 1/10 就判失败"
单档，会把所有正常的压缩器、格式转换都冤枉一遍。

「静默跳过输入」是这一版补的，也是**最像 agent 会犯的错**：每条记录都进过循环，
只是有一部分走了 `except: continue`。它不算失败，因为确实处理了 6 个；但也不算
成功，因为你不知道少了哪 1 个。这一条的价值不在于发现"少了一个"，而在于**指出
是哪个文件、在哪一行被丢掉的**：

```
! 1 个输入文件读过了，但没有对应的产出
  · records
6.json  ←  7_silent_skip.py:11
```

判据刻意保守，只在这几个条件同时成立时才报：输入的**名字能和一个产出对上**（说明
这个脚本确实是"一个输入一个产出"的形态，不是读配置、读模板）、至少 3 个输入
（2 个里少 1 个更可能是设计如此）、且缺的那个没在输出里被提到过。

这条判据的实现也带出了这一版更底层的改动：**每一次 `open()` 现在都记着它是从
哪一行发出的**。审计钩子在事件触发那一刻能拿到调用栈，所以报告里的文件清单会长
这样：

```
新建 (6)
  + records
1.json.tsv  7_silent_skip.py:15
  + records
2.json.tsv  7_silent_skip.py:15
```

「子进程悄悄失败」也有一层刻意的收窄：`git diff` / `grep` / `find` / `diff` 这类
命令**退出码 1 是正常结果**（"有差异"、"没匹配"），不算失败。这一条比抓漏更重要 ——
把 `git push` 失败（退出码 1）报出来是对的，把 `git diff --quiet` 报成失败就是
噪音，用户见过一次误报就会把整个工具关掉。

## 诚实的限制

这个工具的价值建立在对限制的坦诚上，所以它们写在最前面：

- **子进程只看到"起没起、退没退、退出码多少"**。`subprocess.Popen` 的调用会被
  记录（命令、耗时、退出码），比只看到"调了一次"有用得多 —— 「ffmpeg 失败但脚本
  报告成功」就是靠它抓到的。但子进程**内部**的读写看不见：审计钩子只覆盖当前
  Python 进程。所以子进程写了什么，只能靠运行前后的文件快照兜底。
- **脚本必须能在当前解释器里跑**。用的是 `exec` 而不是起子进程，这是审计
  钩子生效的前提。代价是脚本如果 `os._exit()` 或段错误，工具自己也拿不到结果。
- **快照有上限**。默认最多 30000 个文件、单文件 ≤64MB（更大的只比 mtime）。
  超了会在结果里说明，不会假装看全了。
- **不跟随符号链接**，跳过 `node_modules` / `.git` / `__pycache__` 等目录。
- **只验证"改动有没有发生"，不验证"改动对不对"**。它不知道你期望的业务
  结果是什么。
- **"它声称了什么"靠词表读，不是靠理解**。默认认三十多个中英文动词
  （处理/导出/同步/解析/校验…），加上 `files` / `records` 这类量词。
  如果脚本打印的是「吞掉 7 条」这种没见过动词的句子，数量就读不出来，
  "说 N 项却产出 0"这条判据也就没有输入 —— 结果只会是**少报**，不会误报。
- **`ok` 这类短词必须整词命中**。早先用无差别子串匹配，`token 已失效`、
  `cook the books`、`not ok` 全被判成"成功"，一句日志就能让整条结论反过来。
- **`replay` 只跑两次**，所以"两次一致"不等于永远一致 —— 它抓的是必然出现的
  非确定性（随机数、未初始化的状态），抓不到偶发的（比如只在月末出现的分支）。
  两次都在同一秒内跑完时，时间戳差异也不会暴露。副本默认最多 20000 个文件、
  512MB，超出部分不进副本。

## 为什么会有这个东西

AI agent 时代，脚本最危险的状态不是崩溃，是**安静地什么都没做**。
崩溃有堆栈，静默失败只有一行绿色的成功提示。

而 agent 有两个动机让它倾向于"宣布成功"：一是它把 `exit 0` 当成成功的充分
条件；二是"我做完了"比"我没做成"更符合它的输出习惯。

所以这个工具针对的不是别人的 bug，是**自我报告本身**。

## 结构

```
silentaudit/
  trace.py     审计钩子：open / rename / remove / mkdir / subprocess，附带调用行号
  procwatch.py 子进程观测：命令、起止时刻、退出码（钩子看不到的那一半）
  snapshot.py  文件快照与对比（sha 只算一次，大文件退化成 mtime）
  judge.py     三路证据的交叉判决，给出可信度与线索
  expect.py    判断新建的文件是不是"本来就该覆盖那个旧的"
  hints.py     源码里找"最可能解释这次失败"的那一行（只在扣分时启用）
  runner.py    在一个进程里跑脚本并收集证据
  replay.py    在副本里连跑两遍，比较两次结果是否一致
  report.py    终端渲染（自动处理 Windows 的 ANSI 与 UTF-8）
tools/
  test_all.py  144 项自测，一半用例是"正常脚本不能被冤枉"
```

## 自测

```bash
python tools/test_all.py
```

144 项。其中一半的断言是**误报**方向：好脚本必须拿到高分、正常代码不能被
指认成可疑行、正常新建报告不能被当成"写错地方"、`git diff` 退出码 1 不能被
当成子进程失败、脚本的路径和耗时不应当被当成两次运行的差异。一个诊断工具
最大的风险不是漏报，是天天喊狼来了。
