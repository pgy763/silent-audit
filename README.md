# silent-audit

**判断一个脚本的「我干完了」到底可不可信。**

它跑完了，退出码 0，还打印了一句 `迁移完成，处理 1000 行`。
**但文件一个字节都没变。**

这种失败不报错、不抛异常、不留日志。你只有事后去 `git diff` 才会发现。
`silent-audit` 把这件事变成一条命令。

```
$ silent-audit run migrate.py

  不可信：它说的话和事实对不上

  可信度  ██░░░░░░░░░░░░░░░░░░  1.0/10

  它声称     处理 0 项
  系统调用    1 次写入 / 2 次读取
  物证      1 个文件被写 · 其中 0 个真的变了
  退出码     0

  ✗ 退出码 0，报告成功，但磁盘上没有任何文件发生变化
    它跑完了、没报错、打印了成功信息，但所有文件的 md5 与运行前一致。

  ! 1 个文件被写过，但内容与运行前逐字节相同
      · conf.json

  最可疑的几行
      10  r.get("url", "")
          代码里写 "url"，数据里的字段是 "URL"，取值会永远失败
```

第二种形态：**写是写了，写错了地方**。

```
$ silent-audit run overwrite.py

  可疑：有实打实的写入，但报告偏乐观

  可信度  ███████░░░░░░░░░░░░░  3.5/10

  ✗ 1 个新建文件看起来是某个已有文件的副本，而不是覆盖它
    文件名带 (1) / copy / -1 这类后缀，同目录下还留着原名那份。脚本会报告
    "已保存"，你的下游脚本却还在读那个没被更新的旧文件。
      · data(1).csv  ← 本应写入 data.csv
```

## 它凭什么下这个结论

三路独立证据，对不上就报警：

| 证据 | 来源 | 回答的问题 |
|---|---|---|
| **它声称** | 脚本的 stdout / stderr | 它说自己做了什么 |
| **它调用** | `sys.addaudithook` 记的真实 `open` / `rename` / `remove` | 它实际动了什么 |
| **物证** | 运行前后的文件 md5 | 世界到底变了没有 |

关键设计：**不需要改被测脚本一个字符**。审计钩子是 Python 解释器提供的，
在进程内部记录，目标代码完全不知道自己在被观察。

## 装

```bash
pip install -e .
# 或者不装，直接跑
python -m silentaudit run script.py
```

Python ≥ 3.9，零依赖。

## 用

```bash
# 最基本
silent-audit run migrate.py

# 盯住指定目录（默认盯脚本所在目录）
silent-audit run clean.py --watch ./cache --watch ./build

# 被测脚本自己的参数，放在 -- 后面
silent-audit run migrate.py --watch ./data -- --dry-run --verbose

# 写一份 JSON（给 CI / 别的程序用）
silent-audit run migrate.py --json report.json

# 可信度低于 6 就以非 0 退出，可以塞进 CI
silent-audit run migrate.py --fail-under 6

# 允许脚本正常新建文件（避免把"生成报告"当成"写错地方"）
silent-audit run build_report.py --watch . --allow-new '*.html' --allow-new 'out/*'

# 先看看它抓什么（会在当前目录生成五个失败样本）
silent-audit demo
```

## 输出里的「可信度」是什么

不是"代码质量分"，是 **"这个脚本的自我报告有多可信"**。

- `10` —— 它说的、它做的、磁盘上发生的，三边一致
- `6–9` —— 改动是真的，但报告里有些含糊的地方
- `3–6` —— 有实打实的写入，但声称的数字明显对不上
- `0–3` —— 它说的话和事实对不上

一个逻辑完全错误的脚本也可能拿 10 分：**分数高只说明"报告可信"，
不说明业务逻辑正确**。这句话工具里也会打印出来。

## 十种它认得出来的模式

| 模式 | 表现 |
|---|---|
| 声称成功但零变更 | 退出码 0 + 成功字样 + 所有 md5 不变 |
| 自报 0 项却当成功 | `处理 0 行` 后面接着 `完成` |
| 数字对不上 | 说处理 1000 项，只动了 3 个文件 |
| 无效写入 | 文件被写过，但内容和原来逐字节相同 |
| 只读不写 | 读了 500 个文件，一次都没写 |
| 写到别处 | 真实写入发生在 `--watch` 指定的目录之外 |
| **写错地方** | 本该覆盖 `data.csv`，结果另存成 `data(1).csv` |
| **子进程悄悄失败** | 调 `ffmpeg` 转码失败，忘了 `check=True`，仍然打印「完成」 |
| 吞掉部分失败 | 输出里有失败/跳过，但退出码是 0 |
| 源码线索 | 指向 `.get("url", "")` 这种"永远取到空值"的行 |

最后一条只在**已经判定不可信**时才出现 —— 正常脚本不会看到一屏噪音。

「写错地方」这条有个刻意的取舍：只有**名字像副本**（`x(1).csv` / `x copy.csv` /
`x-1.csv`，且同目录下本尊还在）才扣分。单纯"新建了一个没人提过的文件"只作为
提示、不扣分，因为生成报告的脚本天生会新建文件。要压掉误报就加 `--allow-new`。

「子进程悄悄失败」也有一层刻意的收窄：`git diff` / `grep` / `find` / `diff` 这类
命令**退出码 1 是正常结果**（"有差异"、"没匹配"），不算失败。这一条比抓漏更重要 ——
把 `git push` 失败（退出码 1）报出来是对的，把 `git diff --quiet` 报成失败就是
噪音，用户见过一次误报就会把整个工具关掉。

## 诚实的限制

这个工具的价值建立在对限制的坦诚上，所以它们写在最前面：

- **子进程只看到"起没起、退没退、退出码多少"**。`subprocess.Popen` 的调用会被
  记录（命令、耗时、退出码），比只看到"调了一次"有用得多 —— 「ffmpeg 失败但脚本
  报告成功」就是靠它抓到的。但子进程**内部**的读写看不见：审计钩子只覆盖当前
  Python 进程。所以子进程写了什么，只能靠运行前后的文件快照兜底。
- **脚本必须能在当前解释器里跑**。用的是 `exec` 而不是起子进程，这是审计
  钩子生效的前提。代价是脚本如果 `os._exit()` 或段错误，工具自己也拿不到结果。
- **快照有上限**。默认最多 30000 个文件、单文件 ≤64MB（更大的只比 mtime）。
  超了会在结果里说明，不会假装看全了。
- **不跟随符号链接**，跳过 `node_modules` / `.git` / `__pycache__` 等目录。
- **只验证"改动有没有发生"，不验证"改动对不对"**。它不知道你期望的业务
  结果是什么。

## 为什么会有这个东西

AI agent 时代，脚本最危险的状态不是崩溃，是**安静地什么都没做**。
崩溃有堆栈，静默失败只有一行绿色的成功提示。

而 agent 有两个动机让它倾向于"宣布成功"：一是它把 `exit 0` 当成成功的充分
条件；二是"我做完了"比"我没做成"更符合它的输出习惯。

所以这个工具针对的不是别人的 bug，是**自我报告本身**。

## 结构

```
silentaudit/
  trace.py     审计钩子：open / rename / remove / mkdir / subprocess
  procwatch.py 子进程观测：命令、起止时刻、退出码（钩子看不到的那一半）
  snapshot.py  文件快照与对比（sha 只算一次，大文件退化成 mtime）
  judge.py     三路证据的交叉判决，给出可信度与线索
  expect.py    判断新建的文件是不是"本来就该覆盖那个旧的"
  hints.py     源码里找"最可能解释这次失败"的那一行（只在扣分时启用）
  runner.py    在一个进程里跑脚本并收集证据
  report.py    终端渲染（自动处理 Windows 的 ANSI 与 UTF-8）
tools/
  test_all.py  62 项自测，一半用例是"正常脚本不能被冤枉"
```

## 自测

```bash
python tools/test_all.py
```

62 项。其中一半的断言是**误报**方向：好脚本必须拿到高分、正常代码不能被
指认成可疑行、正常新建报告不能被当成"写错地方"、`git diff` 退出码 1 不能被
当成子进程失败。一个诊断工具最大的风险不是漏报，是天天喊狼来了。
